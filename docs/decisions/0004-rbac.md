# ADR 0004: Autorização por papéis (RBAC)

**Status:** Aceito
**Data:** 2026-09-26

## Contexto

O TCC define, no RF06 e no RNF02, controle de acesso baseado em papéis (RBAC), e a RN03 é explícita: *"apenas administradores podem gerenciar usuários e serviços"*, com dois atores (Administrador e Usuário). A "Tela de Gestão de Usuários" descrita no documento mostra o admin cadastrando, editando e excluindo usuários e visualizando papéis de acesso.

Duas decisões precisavam ser tomadas antes de implementar: como o primeiro ADMIN do sistema é criado (não existe mais tenant/organização "dona" do cadastro, ver ADR 0003) e onde a informação de papel fica disponível para as rotas decidirem acesso.

## Decisão 1: Bootstrap do primeiro ADMIN

### Alternativas consideradas

| Alternativa | Prós | Contras |
|---|---|---|
| **Primeiro registro vira ADMIN** *(escolhida)* | Sem passo manual; funciona imediatamente após `npm install` + migration; fácil de testar e demonstrar | Implícito: quem descobrir uma instância vazia primeiro se torna admin — aceitável aqui pois não é multi-tenant público, é uma instância única controlada |
| Todos nascem USER; promoção manual via SQL | Explícito sobre quem é admin | Exige um passo documentado fora da API antes do sistema ser utilizável |
| Seed script dedicado (`npm run seed`) | Mais próximo de prática de mercado (credenciais fixas/geradas) | Mais um artefato para manter, versionar credenciais de seed e explicar na banca |

### Decisão

`POST /auth/register` verifica `prisma.user.count()`: se a tabela estiver vazia, o usuário criado nasce `ADMIN`; caso contrário, `USER`. A troca de papel a partir daí é feita por um `ADMIN` existente via `PATCH /users/:id/role`.

## Decisão 2: Papel no payload do JWT

### Decisão

O `role` do usuário passa a compor o payload do JWT (`sub`, `email`, `role`), ao lado do que já existia (ver ADR 0002). O `RolesGuard` lê `request.user.role`, populado pela `JwtStrategy`, sem precisar consultar o banco a cada requisição — mantém o princípio stateless da API.

### Consequências

- **Papel desatualizado até o token expirar:** se um `ADMIN` promove ou demove um usuário, a sessão já aberta desse usuário continua com o papel antigo até o access token expirar (até 15 minutos, ver ADR 0002) ou até ele chamar `/auth/refresh` (que busca o usuário no banco e emite o papel atual). É o mesmo trade-off já assumido para o refresh token stateless, agora se estendendo ao papel — registrado aqui como limitação conhecida, não como bug.
- **Regra "não remover o último ADMIN":** implementada no `UsersService`, impede demover ou excluir um `ADMIN` quando ele for o único. Sem essa regra, o sistema poderia ficar sem ninguém capaz de gerenciar usuários (lockout).

## Mecanismo (implementação)

- `@Roles(...roles: Role[])` — decorator que marca rota ou controller com os papéis permitidos (`src/auth/decorators/roles.decorator.ts`).
- `RolesGuard` — guard global, registrado depois do `JwtAuthGuard` (`APP_GUARD` no `AppModule`, ordem importa: `RolesGuard` depende de `request.user` já populado). Sem `@Roles()` na rota, não restringe nada além da autenticação já feita pelo `JwtAuthGuard`.
- `UsersModule` (`GET /users`, `PATCH /users/:id/role`, `DELETE /users/:id`) — todo o controller marcado com `@Roles(Role.ADMIN)`, é a aplicação concreta da RN03.
